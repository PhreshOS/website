title: Execution
description: Run a Server as a command, a Node.js worker, or a sandboxed module.
---

A Server runs in one of three modes, chosen in its
[configuration](/docs/sdks/core/program-configuration). The Server SDK, the
Endpoint, and the System behave the same in all of them. What changes is what
the code can do **on its own**, outside the System.

| Mode | Declare | Runs | Can reach on its own |
| --- | --- | --- | --- |
| Command | `command: "./server"` | Any executable | Everything the user running PhreshOS can |
| Worker | `worker: "main.js"` | A JavaScript module in a Node.js Worker | Everything Node.js can |
| Sandbox | `sandbox: "main.js"` | A bundled module in a contained JavaScript runtime | Nothing; only the System |

```ts title="phresh.config.ts"
server: {
  location: "dist/server",
  worker: "main.js",
  devCommand: "vite-node server/main.ts",
}
```

## Development

`phresh dev` always runs the Server with its `devCommand`, as a command,
whatever production mode you chose. Test a `sandbox` Server with
`phresh start` before installing it.

## What stays the same

In every mode, the Server:

- loads its entry, connects the SDK, and becomes ready;
- is stopped by an uncaught exception or unhandled rejected Promise;
- has its `console`, `stdout`, and `stderr` kept in the Program's
  [logs](/docs/system/logs);
- reaches the System only through the SDK, under the Program's
  [permissions](/docs/system/security/permissions).

The SDK never swaps a System operation for a local one. `system.storage` and
`system.network` always go through the System, even when a `worker` could
access files or the network directly. Direct Node.js calls are possible in
`command` and `worker` modes, but they happen outside the System and its
permissions.

## The sandbox

A `sandbox` Server runs in QuickJS, a small JavaScript engine, with a 128 MiB
memory limit. It has no Node.js APIs, no file system, no child processes, and
no direct network access. Everything outside its own code goes through the
System and its permissions, so the owner stays in control of what it does.

It has JavaScript itself, plus:

- `console`, `crypto.randomUUID`, `URL`, `TextEncoder`, `TextDecoder`;
- timers and microtasks;
- `EventTarget`, `AbortController`, and `AbortSignal`;
- streams, `Blob`, `File`, `Headers`, `Request`, and `Response`.

Use `system.network.fetch()` instead of `fetch`, and `program.data` or
`system.storage` instead of files.

A sandbox Server can import relative modules from its own folder, but not
packages by name. Bundle your dependencies into the build:

```ts
// server/main.ts: fine, bundled at build time
import { parse } from "some-package"
```

## Choose a mode

- **Sandbox** for Programs that should do nothing the owner has not allowed.
- **Worker** for JavaScript Servers that need Node.js.
- **Command** for Servers written in another language, or that need to run a
  specific executable.

See [Endpoint execution](/docs/system/security/execution) for how execution modes
fit with permissions.
