A Service lets other Programs reach one of your Endpoints by a stable address,
without owning or even seeing your Program and its Processes. Use it to offer
a capability, such as an editor, a sync engine, or a search index, to the rest
of the System.

A Service is not a separate thing that runs. It is a named Endpoint that chose
to be discoverable, and messages sent to the Service reach that Endpoint.

```ts
const editor = system.service.prepare({
  program: "text-studio",
  process: "editor",
  endpoint: "server",
})

const document = await editor.ask("document.open", { path: "welcome.txt" })
```

## The address

A Service address has three parts:

| Part | Meaning |
| --- | --- |
| `program` | The identity of the Program providing it |
| `process` | The name of the Process, which is also the Service name |
| `endpoint` | `"server"` or `"client"` |

The address points at a role, not at one run. If the Endpoint restarts, or the
named Process is replaced by a new one with the same name, the same address
reaches it again. Only a named Process can provide a Service, because an
unnamed Process has no stable address.

## Provide a Service

Name the Process and mark the Endpoint as a Service:

```ts
await program.createProcess({
  name: "editor",
  server: { service: true },
})
```

The Program can also make an Endpoint a Service by default in its
[definition](/docs/sdks/core/program-configuration). A launch or `start()` can
override that for one run.

The Service becomes available once that Endpoint is running and ready, and
unavailable when it stops. Inside the Endpoint, `context.isService()` reports
whether the current run is a Service.

## Find Services

When you do not know who provides a capability, search by name:

```ts
const editors = await system.service.search("editor")
const all = await system.service.list()
```

Several Programs can offer a Service with the same name, so `search()` can
return more than one. Only available Services that you are allowed to reach
appear.

Follow Services as they appear and disappear:

```ts
system.service.subscribe("available", service => {
  console.log(service.address())
})
system.service.subscribe("unavailable", service => {})
```

These events describe what you can reach. A permission change can add or
remove a Service even when its Endpoint did not start or stop.

## Address a known Service

When you know the address, `prepare()` returns its handle right away, without
contacting the System:

```ts
const editor = system.service.prepare({
  program: "text-studio",
  process: "editor",
  endpoint: "server",
})
```

Preparing a handle does not mean the Service exists or that you may use it.
That is checked when you use it:

```ts
await editor.available()   // whether it is available now
await editor.waitReady()   // wait until it is, 10 seconds by default
```

Preparing the same address again returns the same handle.

## Communicate with it

A Service handle speaks the same language as an Endpoint: you can publish to
it, observe its events, and ask a Server Service questions.

```ts
editor.publish("document.focus", { path: "welcome.txt" })
editor.subscribe("document.changed", change => {})

const saved = await editor.ask("document.save")
const slow = await editor.timeout(30_000).ask("document.export")
```

Only Server Services answer questions. See
[Communication](/docs/runtime/communication).

A Service handle cannot start, stop, or exit the Endpoint behind it. Those
belong to whoever owns the Process.

## Follow its availability

The handle stays valid while its Endpoint comes and goes. Its `lifecycle`
reports each change:

```ts
editor.lifecycle.subscribe("available", () => {})
editor.lifecycle.subscribe("unavailable", () => {})
```

`system.service` events tell you which Services you can reach overall;
`lifecycle` follows one address.

## Show who provides it

While a Service is available, you can read the name, version, and icon of the
Program behind it, without being able to see that Program itself:

```ts
const { name, version } = await editor.programMetadata()
const icon = await editor.programIcon("small")   // PNG Blob
```

Both reject while the Service is unavailable.

## Permissions

Services are reached by name, so access is granted by name. The `services`
permission lists the Service names a Program may reach, such as
`services: ["editor"]`. That grant covers every Service with that name, from
any Program and on either Endpoint.

The `services` and `programs` permissions are independent: reaching a Service
does not reveal its Program, and seeing a Program does not grant its
Services.

This also applies to your own Program's Services, for two reasons:

- You do not need them: your own Endpoints are reachable directly through
  their [Process handles](/docs/runtime/endpoints).
- A Service name is not tied to one Program. Granting a name automatically
  would also grant every Service other Programs offer under the same name.

See [Permissions](/docs/system/security/permissions).

## Reference

| Member | Result |
| --- | --- |
| `system.service.list()` | Available Services you can reach |
| `system.service.search(name)` | Available Services with that name |
| `system.service.prepare(address)` | A handle for that address |
| `service.address()` | Its address |
| `service.available()` | Whether it is available now |
| `service.waitReady(timeout?)` | Resolves when it is available |
| `service.lifecycle` | `available` and `unavailable` events |
| `service.publish(event, payload?)` | Sends a message to its Endpoint |
| `service.subscribe`, `wait`, `events` | What its Endpoint announces; see [Communication](/docs/runtime/communication) |
| `service.ask(event, payload?)`, `timeout(ms)` | Ask a Server Service |
| `service.programMetadata()`, `programIcon(size?)` | Name, version, and icon of its provider |
