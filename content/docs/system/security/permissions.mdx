title: Permissions

Permissions decide which System capabilities a Program may use, such as
reaching other Programs, the network, or files on the machine. They belong to
the Program, so its Server and Client always have the same permissions.

A Program declares what it needs, asks for more while running, and the owner
decides.

```ts
if (!await context.permissions.allows("network", ["https://api.example.com"])) {
  await context.permissions.request("network", ["https://api.example.com"])
}
```

## What a Program can do without permissions

Every Program can always:

- see and manage its own Program, Processes, Endpoints, and Windows;
- use its own files, store, database, and logs;
- read the System's Appearance;
- in a Client, read the Desktop's size and preferences.

Everything beyond that needs a permission.

## The permissions

| Permission | Allows |
| --- | --- |
| `programs` | Seeing and managing all Programs, or selected ones, with their Processes, Windows, and resources |
| `services` | Reaching all [Services](/docs/runtime/services), or those with selected names |
| `layers` | Starting a Client in `under`, `over`, `wallpaper`, or `shell`, or in selected ones; see [Layers](/docs/system/desktop#layers) |
| `network` | Requests to all URLs, or to selected URL patterns; see [Network](/docs/system/network#permissions) |
| `storage` | Files on the machine, all or selected paths and operations; see [Storage](/docs/system/storage#files-on-the-machine) |
| `uploads` | Creating [uploads](/docs/system/storage#uploads) |
| `logs` | Reading the [System log](/docs/system/logs) |
| `appearance` | Changing [Appearance](/docs/system/appearance) |
| `desktopPreferences` | Changing [Desktop preferences](/docs/system/desktop#preferences) |
| `desktopConnection` | Reading the Desktop's [Connection](/docs/system/security/authentication) and its Session |
| `authentication` | Managing owner credentials, Connections, and Sessions. Includes `desktopConnection` |
| `all` | Everything, including creating Programs, assigning permissions, and [`system.shell()`](/docs/system/shell) |

`programs` and `services` are independent: reaching a Service does not reveal
its Program, and seeing a Program does not grant its Services.

## Declare what you need

List the permissions your Program needs in its
[configuration](/docs/sdks/core/program-configuration):

```ts title="phresh.config.ts"
permissions: {
  network: ["https://api.example.com"],
  services: ["editor"],
  uploads: true,
}
```

`true` asks for the whole permission; a list asks for selected values.

A declaration is a default, not a grant written into the System. When the
owner has made a decision about a permission, that decision applies instead.

## Check and request at runtime

Inside an Endpoint, `context.permissions` reads the Program's current
permissions:

```ts
await context.permissions.get("network")     // its current value
await context.permissions.all()              // every permission
await context.permissions.allows("network", ["https://api.example.com"])
```

`request()` asks the owner and resolves with the decision:

```ts
const result = await context.permissions.request("services", ["editor"])
// the granted list, false when denied, or null when dismissed or expired
```

It resolves at once when the Program already has exactly that value.
Otherwise the Desktop asks the owner. Approval replaces the whole permission
with the requested value, so asking for a different value, even a smaller
one, still needs a decision.

A request waits two minutes by default. Change it with `timeout()`:

```ts
await context.permissions.timeout(300_000).request("storage", ["read:Documents/**"])
```

A request ends with `null` if the Endpoint that made it stops. Only a running
Endpoint can make requests, so a request always comes from a known Program.

## Missing permissions

What happens without a permission depends on what you do:

- **Looking something up** behaves as if it did not exist: `find()` returns
  `null` and `list()` leaves it out. This way a Program cannot learn that
  hidden software exists.
- **Using a capability** you already know about, such as changing Appearance,
  rejects with an error.

Events follow the same rule: you only hear about what you can see.

## Manage a Program's permissions

`program.permissions` reads and sets any visible Program's permissions:

```ts
const program = await system.program.find("notes")

await program.permissions.get("network")
await program.permissions.allows("uploads")

await program.permissions.allow("network", ["https://api.example.com"])
await program.permissions.allow("uploads")       // the whole permission
await program.permissions.deny("network")        // an explicit no
```

`allow()` replaces the permission's value; it does not add to it. Setting
permissions requires `all`.

A Program emits `permissions` when its permissions change. See
[Programs](/docs/runtime/programs#observe-changes).

## Decide requests

A Program that replaces the Shell, such as a custom settings or security
interface, can decide requests through `system.permissions`:

```ts
system.permissions.subscribe("permissionRequest", async request => {
  console.log(request.from, request.name, request.scope, request.expiresAt)

  await request.allow()    // grant the requested value
  // or: request.deny()    // store an explicit no
  // or: request.cancel()  // end the request, change nothing
})

await system.permissions.requests()   // requests pending now
```

`permissionResolve` reports how each request ended. After a request ends, its
details stay readable, but `allow()`, `deny()`, and `cancel()` reject.

This requires `all`. Deciding a request can grant any permission, including
`all` itself, so a narrower permission for it would amount to `all` anyway.

The System only records requests and decisions. How a request is shown to the
owner is up to the Shell.

## How values work

Each permission has one of three values:

| Value | Meaning |
| --- | --- |
| A list | Granted. An empty list grants the whole permission; a non-empty list grants only those values |
| `false` | Explicitly denied |
| `null` | No decision |

When a permission has a decision of its own, it is used even if the Program
has `all`. That lets the owner grant `all` and still deny one thing.

A broader permission also allows everything it contains. For example,
`authentication` includes `desktopConnection`, and `all` includes everything
without a decision of its own.

## What permissions do not limit

Permissions govern what a Program does through the System. They do not take
away what its environment already allows: a Client still has browser APIs,
and a `command` or `worker` Server still has host access. A `sandbox` Server
has no host access of its own, so the System and its permissions are its only
way out. See [Endpoint execution](/docs/system/security/execution).

Node scripts and the CLI connect as the owner and are not limited by Program
permissions.

## Reference

| Member | Result |
| --- | --- |
| `context.permissions.get(name)`, `all()`, `allows(name, value?)` | Read the Program's permissions |
| `context.permissions.request(name, value?)` | Ask the owner |
| `context.permissions.timeout(ms)` | Requests with another deadline |
| `program.permissions.get()`, `all()`, `allows()` | Read a Program's permissions |
| `program.permissions.allow(name, value?)`, `deny(name)` | Set them; requires `all` |
| `system.permissions.requests()` | Pending requests; requires `all` |
| `system.permissions` events | `permissionRequest`, `permissionResolve` |
| `request.allow()`, `deny()`, `cancel()`, `pending()` | Decide one request |
